まず、プロジェクトに小さな機能を追加しました。より大規模な変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存の開発フローに沿って動作し、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue から新機能を生成し、コードの妥当性と機能の動作を確認して、最終的にプロジェクトに正常にマージします。

> [!NOTE]
> 機能のワークフローを続ける間は、同じセッションを使います。通常は扱うファイルの種類ごとにセッションや PR を分けますが、ここでは中心的な概念に集中するため手順を簡略化しています。

このレッスンでは、次のことを行います。

- GitHub Issue から新しいエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新しい機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズして、MCP 検証を追加し、QA エージェントを作成して、機能の PR を作成します。

## シナリオ

Tailspin Toys のカタログが増えており、訪問者がカテゴリや発行者でゲームを絞り込めるようにする必要があります。バックログの Issue には機能が記載されていますが、カテゴリを組み合わせる方法などはコーディング前に合意が必要です。Plan モードで決定事項を整理してから、範囲を限定した実装を Autopilot に任せます。

## 背景

AI コーディングエージェントを開発フローに加えても、基本は変わりません。むしろ基本がさらに重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細を記載した Issue を開きます。
2. 構築する内容を計画します。
3. コードを構築してレビューします。
4. テストを実行してコードを検証します。
5. 新しい機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューと継続的インテグレーションのプロセスが成功したら、コードをマージします。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを基にしています。

この標準的なアプローチに従うことで、AI が生成したコードが要件を満たし、手作業のコードと同じレビューを受けるようにできます。

## セッションモード

**セッションモード**は、エージェントの自律性を制御します。プロンプト欄の下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントが変更を提案し、次に進む前に入力を待つため、共同で作業します。
- **Plan**: エージェントが最初に計画を作成します。エージェントが実行する前に、計画をレビューして承認します。
- **Autopilot**: エージェントが完全に自律してコードを書き、テストを実行し、入力を待たずに反復します。

まず Plan モードで計画を確認し、その後 Autopilot で実装します。

## Issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys のリポジトリフォルダーを選び、リポジトリ上部のナビゲーションから **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これは既存の Issue なので、新たに作成する必要はありません。
2. **New session** を選び、更新済みの `main` を基にする **new working tree** を選択します。

   ![GitHub Copilot app の Issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで失敗する場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了してから再度開きます。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## フィルタリング機能を計画する

計画を立てると、Copilot がコードを書く前にアプローチをレビューできます。Issue から始めたため、Copilot は機能リクエストをすでにコンテキストとして把握しています。次を送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画を Issue の受け入れ条件と照らし合わせます。カテゴリと発行者によるフィルタリング、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数のカテゴリをどう組み合わせるか、ゲームが一致しない場合に何を表示するかなど、不明な動作について話し合います。

計画には、プロジェクトにあるツールを使った lint、単体テスト、E2E テスト、型チェックを含めます。フィルタリングの実装とテストに範囲を絞り、品質ワークフローを完了してから PR を作成します。承認前に計画の修正を依頼し、後で検証できるよう Issue の URL と合意した補足事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan** または使用中のバージョンで表示される同等のオプションを選択します。承認によってモードが切り替わったと決めつけず、現在のモードを確認してください。モード表示が **Autopilot** になっていることを確かめます。

Copilot が実装を始めます。決めた計画に沿って、コードの生成やテストを実行しながら反復します。

> [!NOTE]
> 承認するとすぐに実装が始まることがあるため、先に計画をレビューします。Copilot から依存関係の不足やポート競合が報告された場合は、チェックを完了と判断する前にセットアップの問題を解決します。自分で起動したサーバーのみを停止してください。

## 実装をレビューして検証する

生成されたコードは、ほかのコードと同様にマージ前にレビューします。コードを確認してサイトを実行し、動作を確かめましょう。

1. **Changes** を開き、フィルタリングの実装とテストを確認します。
2. 複数カテゴリと発行者の組み合わせも含め、結果を Issue と承認した追加の決定事項に照らし合わせます。変更が既存のリポジトリ指示に従っていることも確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を承認する前に失敗を解消し、影響を受けるチェックを再実行します。Playwright の E2E 設定はプレビューをビルドして配信し、ローカルサーバーを再利用することがあります。テスト対象が以前のレッスンではなく、この worktree のサーバーであることを確認してください。

## 新しい機能を確認する

コードに問題がないように見えても、実際に動作するでしょうか。アプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトで、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

   ```plaintext
   Start the app and open it in the browser canvas.
   ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリを選び、表示結果が選択したカテゴリに一致することを確認します。フィルターを解除してから発行者を選び、結果が一致することを確認します。
4. カテゴリと発行者を組み合わせ、結果を Issue と承認した計画に照らし合わせます。複数カテゴリに対応する場合は、合意した組み合わせの動作を確認します。
5. 該当するゲームがない組み合わせを試して、空の状態を確認します。フィルターを解除またはリセットし、全件が表示されることを確かめます。
6. 確認が終わったら、次のプロンプトでこのセッションが起動した開発サーバーを停止するよう Copilot に依頼します。

   ```plaintext
   Stop the dev server and close the browser canvas.
   ```

## 次のレッスンに向けてセッションを保持する

フィルタリングの PR はまだ作成もマージもしないでください。レッスン 4 から 8 まで、同じセッション、worktree、ブランチを使います。次のレッスンではフィルタリングのコードにカスタム指示を適用し、その後にスキルと QA の改善を追加して、レッスン 8 でまとめた PR を作成し、マージします。開発サーバーを停止した後はセッションをそのままにして、次のレッスンで再開してください。

- GitHub Issue から新しいエージェントセッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードで新しい機能を実装しました。
- コードをレビューしました。
- ブラウザーキャンバスで機能を手動で検証しました。
